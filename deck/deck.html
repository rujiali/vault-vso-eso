Vault Secrets Operator vs External Secrets Operator
A side-by-side lab: Vault Enterprise 2.1 · VSO 1.6 · ESO · Postgres · kind

Set expectations. This is a live comparison, not a slide-ware argument. Everything that differs on screen comes down to the operator, because Vault, the policies and the app are the same on both sides.

Before starting: the lab should have been up for at least 20 minutes so the database and certificate scenarios have some history.

The question

Getting Vault secrets into a pod is easy. Keeping them fresh, short-lived and cleaned up is the real job.

Freshness

When a secret rotates, how long until every workload is running on the new value?

Lifecycle

Who renews dynamic credentials, and who revokes them when a workload goes away?

Operations

What happens when the operator restarts, and who supports it when it breaks?

Both operators sync Vault data into Kubernetes Secrets. The differences are in these three areas.

Frame the evaluation around outcomes the client's security and platform teams care about, not feature lists. These three questions map to the demo scenarios that follow.

Scenario 2 · Rotation

Events vs polling: how fast does a rotation land?

Polling also means constant reads and audit noise on Vault, even when nothing changes.Livedemo/rotate-kv.sh

Run demo/rotate-kv.sh and watch row 1. VSO: the Secret updates within about a second and the note shows when the app was running on the new value. ESO: the Secret updates on the next poll, then the badge goes amber and stays amber.

The diagram is schematic. Read the real timings off the dashboard notes.

Incident framing: the number that matters is how long until every workload is running on the new value, not just how long until the Secret object changes.

Likely objection: "Why not just set ESO to poll every 10 seconds?" Answer: you can, but then every ExternalSecret reads Vault every 10 seconds whether anything changed or not. That's constant load and a flood of audit log entries to ship to your SIEM, it grows with every secret and every cluster, and it still doesn't restart the app. Events only cost something when a secret actually changes.

Scenario 4 · Dynamic database credentials

Who owns the lease?

VSO: one credential, renewed, revoked on delete. ESO: a new credential each refresh, old ones left to expire.Livedemo/leases.sh

The main event. Switch to the terminal running demo/leases.sh. VSO: one lease, one Postgres user, the valid-until time moves forward when it renews. ESO: several live users, each waiting to expire. Meanwhile the ESO app is still using the username it started with (dashboard row 2, amber).

Then show dashboard row 2. Each app logs in to Postgres every 10 seconds with the credential it started with. VSO stays "Login OK". ESO turns red, "app can't log in to Postgres", about 10 minutes after its app started, because Vault expired the credential it is still holding. Optional: restart the ESO app to show it goes green on the latest credential and red again 10 minutes later.

Check in rehearsal: recent ESO releases added clean-up for some generators. If your installed version revokes leases, lead with renewal and the in-use credential instead of orphaned credentials.

Summary

VSO for Vault. ESO for what isn't in Vault.

Choose VSO when

  • Vault is the system of record
  • You use dynamic credentials or PKI
  • Rotation needs to land in seconds
  • You want it under the same support contract as Vault Enterprise

Where ESO still fits

  • Secrets that live in other stores, such as AWS Secrets Manager or Azure Key Vault
  • Pushing secrets from Kubernetes back to a store (PushSecret)
Anything that lives in Vault: VSO.

Keep the ESO column. Acknowledging where ESO genuinely fits is what makes "VSO for Vault" credible to engineers who already like ESO. Every ESO reason here is about secrets outside Vault, so the conclusion for Vault stays clear.

If they push back with "our secrets rarely change, so polling is fine": dynamic credentials, PKI and lease cleanup still apply, and a rotation forced by an incident still has to land fast.
